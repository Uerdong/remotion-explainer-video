# 各环节适配的模型与工具

选型原则：**能确定性渲染的画面交给代码，能逐段精确计时的语音交给 TTS，只有"真实感素材"才交给生成模型。** 科普 MG 动画的主体绝不要交给视频生成模型，否则时序、文字、卡点全部失控。

## 一、总表

| 环节 | 首选 | 备选 | 为什么 |
|---|---|---|---|
| 选题拆解、文案、分镜脚本 | 当前对话的文本大模型 | 无 | 短文本、强结构，直接产出即可 |
| 配音 TTS | 豆包语音合成（`seed-audio` skill / 语音合成工具） | 任意中文 TTS | 需逐段独立出 wav，便于量时长与重排时间轴 |
| 背景音乐 | 自合成（Python + soundfile，确定性、可钉 BPM） | 曲库选曲后实测 BPM | 曲库难命中"简约知性"，自合成可精确对齐节拍网格 |
| 关键动作音效 | 自合成（正弦/噪声/包络） | 曲库音效包 | 时长、峰值、触发点都要写死，合成最稳 |
| 画面本体 | Remotion（React + interpolate/spring） | 无 | 唯一能保证帧级卡点与零漂移的方案 |
| 封面 / KV | `seedream_5.0_flash`（快）或 `seedream_5.0_pro`（文字精细） | `seedream_4.5` | 单张传播物料，走 pure-image 路线出终图 |
| 真实感空镜 / 过场素材 | `seedance_2.0_fast`（4–15s）、`seedance_2.5`（4–30s） | — | 只在需要实拍感素材时用，不作主体 |
| 音频后处理 / 分离 / 转码 | `byted-mediakit-audio` | ffmpeg | 需要人声分离、码流适配时 |
| 成片剪辑 / 合流 / 字幕压制 | `byted-mediakit-editing` | ffmpeg | 需要多轨混合、加字幕时 |
| 封面设计（需要可编辑/系列） | `doubao-creative-design`（pure-image 或 ai-coding） | 代码渲染（Remotion still） | 已有视觉规范时优先代码渲染，字不会糊 |
| 发布文案撰写 | `doubao-newmedia-writing`（可选） | 直接写 | 需要多平台改写时再上 |
| 渲染执行 | 本地 Node + `npx remotion render` | — | 云端无 Chrome 时不可用 |

## 二、TTS 用法要点

- **每段单独合成一个 wav**，不要一次读整篇再切。段落边界要靠"实测该段时长"，整篇合成后无法精确切。
- 固定同一音色、同一语速、同一采样率，用 f0 中位数抽检是否确实是同一把声音（示例：六段 f0 中位 145.7–171.1 Hz，可判定同一男声）。
- 中文语速经验值 **≈3.3 字/秒**（含标点停顿）。用它反推"目标秒数能容纳多少字"，比写完再删高效。
- 合成后立刻记录每段时长表（如 `s1 7.68s / s2 10.38s / …`），这份表就是下游时间轴的输入。

## 三、图像模型用法要点

- **画面内要出现中文时**，模型只负责"氛围 + 大字块"，精确文字优先用代码渲染或 HTML；AI 生成的中文必须逐字核验，错了只记录 `delivered_with_text_issue`，等用户明确要求再改。
- 输出尺寸常大于请求（请求 1920×1080 实际给 2730×1536），等比放大不影响使用，但**不可非等比拉伸**。
- 一张图只放 3–5 处文字；每多一处，错字概率显著上升。
- 封面三类构图可复用：字图咬合（标题压主体）、结构型主视觉（收益矩阵/流程图当骨架）、压角留白（文字压一角）。

## 四、不要做的事

- 不要用视频生成模型做讲解动画主体：镜头无法钉在 17.3 帧一拍的网格上。
- 不要让 AI 生成图承担"必须准确的数字/公式"：矩阵里的 1年/5年/10年必须代码画。
- 不要在云端渲染：Remotion 需要真实 Chrome，本地跑最稳。
- 不要把 BGM 交给"AI 生成音乐"再事后测 BPM：自合成 + 已知 BPM 才是可复现的。
